# RETRO · 《显影》全流程复盘

> 实测方式：webapi(18360) + 浏览器真实操作，DeepSeek 全程真实调用。成品：3 章短篇《显影》（正文 1539~1821 字/章），PLAN 6/6，git 32 提交，问题清单 43 条全裁决，红线零泄露。结论先行：**流程跑得通，但平台把「流程引擎」的角色转嫁给了用户；成品可读性差的主因不是模型，而是提示词工程与开书脚手架的缺失。**

## 1. 工作流复盘：六项不足（实测证据）

实测一本 3 章短篇的人工成本：**约 80 次点按**——bash 只读审批 ~8 次、提议接受 ~24 次、问题裁决 43 次、阶段确认 6 次。外推 300 章长篇 ≈ 数千次点按，不可持续。

### 1.1 零引导落地（最严重）

- 新建作品 = 一个名字输入框 → 直接进空工作台；全应用 grep `教程|tour|onboard|引导|欢迎|first-run` **0 命中**。
- 12 个生产力命令全部藏在「输入 / 之后」的补全里（`ChatPane.tsx` detectMenu），空态提示仅一行「用 / 调技能、@ 引用素材」。
- 实测中驱动者（本 Agent）是知道流水线语义的开发者，尚且依赖 slash 命令 + 长 prompt（设定阶段一条消息 900+ 字）；**普通作者既不知道命令存在，也不知道「卷号-章号」这种工程语义**。学习成本高于直接用 coding agent——coding agent 用户只需描述任务，这里还要求学平台内部概念。

### 1.2 PLAN 条提示不可执行

`nextHint`（PlanBar.tsx）「完成本章正文与账本回写后确认推进」是纯文本 span。「下一步」与「能点的东西」分离：用户要自己把「完成章纲产物」翻译成 `/章纲 1 1`。阶段确认按钮存在，但对应动作没有直达入口。

### 1.3 HITL 确认疲劳

- git status / git ls-files 这类白名单只读命令逐条确认（实测 ~8 次，全部是无风险查询）。
- 同一文件的连续小修正逐条接受（ch-002 工艺修正、账本用词对齐、账本漏网同步……每次一轮提议-接受）。
- 「完全访问」档存在且有效，但只有 /goal 的启动 toast 推荐它；正常写作流中没有任何降噪引导。
- 审校把 25 条措辞级建议原样甩给作者裁决——真实编辑会先分诊再上报。43 条裁决里作者真正需要的决策 < 10 条。

### 1.4 决策埋在千字长文里

root agent 回复动辄 1000+ 字，「两点请你裁决」「三个待你拍板」埋在段落中间，读者要自己扫描提取。需要结构化决策卡（选项 + 推荐 + 一键采纳），而不是靠作者从长文里找问题。

### 1.5 过程不可见

子 agent 写正文 60~90s，聊天流只显示工具轨迹（read_file 列表），无正文流式预览、无中断入口。作者在最长等待期处于盲区。

### 1.6 与裸 coding agent 相比的价值感薄弱

平台差异化 = 流水线门 / 账本 / 可见性红线 / diff 审阅 / 子 agent 团队——这些是「不出错」的保证；但**「写得好」的脚手架（模板、方法论、文风工程）几乎为零**（§2），而这恰是作者最能感知的价值。附带观察：755 万 tokens / 5000 字成品，输入占 96%（子 agent 每次全量重装上下文），成本效率有数量级优化空间。

## 2. 质量复盘：成品可读性差的根因链

成品症状（用户评价「可读性很糟糕，很多不知所谓的描写」，属实）：

- **无指向细节**：ch-002 开头三连氛围填充（屋檐淌水线/潮气钻墙缝/玻璃蒙水汽，无一承担叙事功能）；ch-003「有辆自行车从门口过去，铃响了一下」。
- **点情旁白**：ch-002「开这扇门，不是要违逆。是不甘心——」（情绪直给）；ch-002「手是熟的。他不太想承认」。
- **均质节奏**：ch-002/003 几乎每段 1-2 行的 staccato，通篇一个节奏——「短句为主」被执行成了 tic。
- **情节密度低**：每章约 1 个事件；ch-001 是慢热氛围开场（回来第五天清点遗物），按网文「黄金三章」标准是留存杀手。

根因（按影响排序）：

1. **文风指令是抽象形容词，无正例**。全装配唯一的风格信号是 6 行 bullet（「平实克制、短句为主、多用感官细节」）。模型把「多感官细节」优化成装饰性填充、把「短句」优化成单调断句——指令式风格约束在长文本上必然漂移，正例（few-shot 样本）远比形容词有效（§4）。**平台没有任何样章/范文锚点机制。**
2. **章纲 = beat sheet**。章纲模板（目标/情节点带字数/冲突/钩子）让正文变成「逐点填肉」：每个情节点分到 ~250 字，只能概述不能成戏（「然后他…」「到夜里他给自己定下来一件事」）。真实作者流程中有**细纲层**（每章：核心事件/开篇钩子/章尾悬念/场景进出/对话要点，见 §4），我们没有——章纲与正文之间缺一层场景级结构。
3. **人物卡只有履历没有「人」**。2-3 句生平事实，无欲望/恐惧/矛盾/说话方式样本。对话质量全靠模型脑补（本次夏晚的对白是运气好）。
4. **审校只查一致性不查可读性**。review-consistency 规程 = 矛盾核对 + 去AI味腔调清单；「细节有无功能、节奏是否均质、情节密度够不够」不在任何 pass 里。去 AI 味是可选命令，不是正文落稿的默认下一站。
5. **开书阶段（用户点名）过于单薄**。设定/总纲/卷纲由用户口述、Agent 整理；没有访谈、没有结构模板（三幕/升级/悬疑倒推）、没有开篇策略（黄金三章）、文风卡与人物卡没有字段规范。开书质量上限 = 用户当次 prompt 的质量。
6. **模型与用途不匹配**。全流程一个 deepseek-flash；按 agent 配模型后端已支持（`resolve_model_id` 按 spec.id 查 `agent_overrides`），前端只有子 Agent 级 UI，且 Settings 页文案「可在下方按 Agent 覆盖模型」指向不存在的区块。

- [网文大纲细纲三要素（核心事件/开篇钩子/章尾悬念）](https://www.wangwen666.com/post/338.html)、[情节细纲字段（事件/场景/亮点/转场，Processon）](https://www.processon.com/view/672da65de62924419e573897)

- [Notion 雪花写作法模板](https://www.notion.com/zh-cn/templates/the-snowflake-method)、[知乎：人物宝典搭建教程（附模板）](https://zhuanlan.zhihu.com/p/653190295)——人物档案字段：动机/目标/冲突/顿悟/成长弧线，一页纸人物 → 整页小传。

**AI 写作提示词与修改**

- [用 AI 写小说的文风微调与风格模仿：Few-shot 模板实战](https://segmentfault.com/a/1190000048136002)（[oschina 镜像](https://my.oschina.net/u/3364816/blog/19746426)）——System Prompt 后接 2~3 个 ~500 字强风格样本，拟合度显著提升；正例远胜形容词指令。
